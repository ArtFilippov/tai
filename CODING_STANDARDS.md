# Python coding standards for code review

Review changed Python code against the applicable rules below. For each finding, cite the location, explain the maintainability or correctness cost, and propose a concrete fix. Prefer existing project conventions over a stylistic preference. Counts and naming patterns are prompts to inspect a design, not grounds for a finding on their own.

## Names and contracts

- **Name classes for what their objects are, not what they do.** Prefer `Invoice`, `FilteredRows`, or `WebPage` to `InvoiceFormatter`, `RowFilter`, or a vague `Helper` or `Manager`. Treat action-derived `-er`/`-or` names such as `Reader`, `Validator`, and `Controller` as signs of a procedural helper; name the represented entity and give its operations appropriate method names instead. Established nouns that denote entities, such as `User` or `Computer`, are not action-derived class names.
- **Separate builders from manipulators.** Use `snake_case`. A builder produces and returns a result without changing the entity it represents; name it with a noun (`total`, `content`). Name a Boolean builder with an adjective (`empty`, `readable`, `present`), without an `is_` or `has_` prefix. A manipulator changes the represented resource; name it with a verb (`save`, `send`) and return no value (`None` in Python). If callers need information about an action, give that operation its own object with separate methods for acting and reporting the result; do not combine both roles in one method.
- **Keep public APIs focused.** Watch for an unjustified growth in public methods or unrelated fields: it may signal multiple responsibilities. Extract a collaborator when it makes the contract more coherent; assess the design rather than applying a fixed count.
- **Depend on the smallest useful interface.** Give project-defined classes an explicit, meaningful contract: a small `typing.Protocol` for structural typing, an `abc.ABC` when shared implementation or runtime enforcement is needed, or a genuine external base when the class extends it. Define the operations callers rely on, even if there is only one implementation; do not mechanically copy every member into a contract or inherit from `object` just to satisfy a checker.
- **Put convenience behavior beside the core contract.** Keep a protocol's required methods minimal. Provide shared convenience operations with a wrapper or collaborating object instead of making every implementation duplicate them.
- **Expose behavior rather than storage layout.** Callers should not directly read, assign, or delete another project-defined object's stored instance fields, including fields of simple data objects. Expose a domain operation or a noun-named answer such as `dollars()`; it may simply return an encapsulated value, provided its public name describes the domain concept rather than the field's storage. A read-only `@property` with the same meaning is also suitable in Python. Avoid `get_x`/`set_x` pairs and writable property setters. Methods within the owning class may access its stored fields directly.
- **Keep constants local to their meaning.** Do not expose public constants or use `enum.Enum`: they expose data and encourage callers to branch on it. A shared literal couples otherwise independent clients to one value and makes each client supply its meaning. Keep technical literals local to their implementation, even if this repeats a literal in unrelated places; put shared domain choices behind objects with behavior instead.

## Construction and dependencies

- **Establish state in one place.** Initialize instance state in `__init__` (or a dataclass's generated initializer) without alternative `@classmethod` constructors. When a frequently used composition needs a name, use an Envelope: an object that implements the same contract, assembles its collaborators, and delegates work to them. Keep input conversion out of the primary constructor or defer it until the object's behavior is used. A newly constructed object must already have all the state needed to fulfill its contract; deferring work is not a reason to require callers to complete its initialization later.
- **Make construction unsurprising.** Assign dependencies and compose lightweight objects in `__init__`; use simple inline `if`/`raise` checks for invalid arguments or `assert` for internal invariants. Do not call project-defined validation helpers or factories, parse expensive input, perform network or file I/O, or use loops, `try`, or `with` in the constructor. Put work behind an explicit operation or documented resource boundary.
- **Make collaborators replaceable.** Pass network clients, repositories, clocks, and similar external dependencies into the object rather than constructing or retrieving them from module-level singletons inside business methods. A convenient default is fine if callers can still supply a substitute.
- **Give objects something to encapsulate.** A project-defined class with no meaningful state may be a procedural helper in disguise: look for a missing collaborator or coordinate of the entity it represents. Put domain behavior in objects that encapsulate what they need, rather than scattering it across utility functions or static methods. Ordinary functions remain appropriate as glue at Python or third-party API boundaries.
- **Compose behavior through small objects when useful.** A wrapper can add caching, filtering, or retries to an existing interface. Prefer composition to inheritance or global helpers when independent behaviors need to be combined.

## State and behavior

- **Keep objects immutable.** Do not rebind an object's encapsulated state after construction; when a value such as money or coordinates changes meaning, return a new object. An immutable object can also remain loyal to a mutable resource whose coordinates it encapsulates, whether that resource is a web page, file, or deliberately represented area of memory. `@dataclass(frozen=True)` only prevents rebinding attributes; a mutable member does not automatically make an object an immutable representative of a resource. Deferring a computation does not justify filling a field on the represented object on first access: that is a state change, not merely lazy work. If caching is needed, put the cached result in a separate caching wrapper rather than silently modifying the represented object.
- **Distinguish state from represented data.** A `WebPage` holding a URL may keep the same identity even when the page's contents change; an object holding a stable reference to an in-memory collection may likewise represent data that changes. Review whether a method updates the same represented resource or silently repoints the object to a different one. For a constant value or collection, return a new object instead of modifying its contents.
- **Keep resource changes consistent on failure.** When an operation changes a represented resource, check whether a failure could leave it partially updated in violation of its contract. Validate or stage changes before applying them, or use a transaction or rollback where consistency requires it. Immutable object fields alone do not make changes to files, repositories, or other resources atomic.
- **Do not use `None` as an argument.** When an input may be absent, pass an object implementing the same contract with appropriate behavior, or offer a separate operation if the action itself differs. Do not use nullable or sentinel arguments to make callers and callees branch on presence.
- **Avoid type introspection and casting to choose behavior.** Do not use `isinstance`, `type(...)`, or `typing.cast` to discover extra capabilities of a project-defined object; this hides a dependency on its concrete type. Express the needed operation in a shared contract and let the object decide how to perform it. At a boundary with untyped input or a third-party API, a type check may validate the input's shape before creating or invoking a domain object; it should not select between implementations of a domain operation.
- **Treat project-owned implementations as complete or abstract.** Do not subclass a complete project-owned class to change its behavior; prefer composition. Extend an incomplete `abc.ABC` only to fill in its documented `@abstractmethod` hooks, without overriding implemented methods that are not extension points. A third-party base class may require subclassing and overriding methods for integration: follow its documented extension points and contract.

## Tests

- **Show the public behavior in tests.** Cover representative use, edge cases, and failures with readable examples. A test should clarify what a caller can rely on; prose is still useful for contracts or rationale that tests cannot convey.
- **Use fakes instead of mocks.** Supply a reusable behavioral fake alongside each project-owned interface so clients can test against the same contract without a network or database; an in-memory repository or local fake client can serve this role. Assert public results and observable effects through the fake, not which collaborator methods were called or how many times. Use a mock only as a last resort when a suitable fake cannot be provided, without tying the test to private implementation steps.

## Results, failures, and resources

- **Model absence without returning `None`.** If a requested single object cannot be found, raise a meaningful exception, return a collection that may be empty, or return an object with the same contract whose absent-case behavior is explicit. Choose a result shape that matches the operation; do not fabricate success or use unexplained sentinels such as `-1`. Manipulators and Python constructors return no value (`None` in Python).
- **Fail fast and carry error context to the application boundary.** Do not use exceptions for ordinary branching or replace a failure with `None`, `-1`, or a fabricated fallback. Let an exception propagate, or catch it to add meaningful context and immediately re-raise with its cause (`raise DomainError(...) from exc`); do not catch and log without propagation. Resolve the failure once at an application entry point, such as a command, request handler, or worker boundary. Prefer one project-defined exception type for translated application failures, with contextual messages and original causes, rather than a hierarchy used for branching. Python has no checked exceptions, so make consequential failures clear in the public contract where callers need to know about them. Put retries for known transient failures in a separate decorator or wrapper rather than mixing recovery into the operation.
- **Release resources deterministically.** Use `with`, `contextlib`, or `try/finally` for files, locks, transactions, sockets, and other resources with a defined lifetime. Do not depend on `__del__` or garbage collection for prompt cleanup.
