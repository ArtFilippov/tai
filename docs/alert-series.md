# Серия запусков по ALERT

Контракт [#16](https://github.com/ArtFilippov/tai/issues/16), расширенный
[#23](https://github.com/ArtFilippov/tai/issues/23), часть
[#13](https://github.com/ArtFilippov/tai/issues/13). Входы — публичный
[`load_alert_manifest`](alert-manifest.md) и [модельный профиль](model-evaluator.md).
Термин «серия запусков» определён в [`CONTEXT.md`](../CONTEXT.md).

Стратегию задаёт `[attack].type`: `fitd` (также по умолчанию),
`adaptive_attacks` или `badchars_deletion`. Для [Adaptive Attacks](adaptive-attacks.md)
используйте `--profile examples/adaptive-attacks-qwen.toml --jobs 1`, для
[Bad Characters/deletion](badchars-deletion.md) —
`--profile examples/badchars-deletion-qwen.toml --jobs 1` с `--extra qwen` в uv.
Обоим профилям нужны Target и модельный оценщик; Attacker не создаётся.
Один base остаётся одной записью независимо от количества вариантов.
Пять cached-суффиксов, deletion-профиль `1 / 8 / 4` (до 32 вариантов) и
ранняя остановка по оценке описаны в документации стратегий;
`run.max_calls_per_conv` применяется только к FITD.

## Команда

Из корня проекта с подготовленными зависимостями и локальными весами:

```bash
uv run --locked tai alert-series --jobs 4 \
    --manifest examples/alert-manifest.json \
    --profile examples/fitd-alert-vllm.toml \
    --taxonomy ALERT_taxonomy.md \
    --artifacts-dir runs/alert-vllm
```

Пути манифеста, профиля и каталога артефактов обязательны; `--taxonomy` по умолчанию
равен `ALERT_taxonomy.md`. Относительные пути считаются от рабочего каталога, в том
числе настройки кеша в профиле. Каталог артефактов создаётся при необходимости.
Повтор команды создаёт отдельный UUID серии, даже при идентичных входах.
`--jobs` — положительное целое, default **4**; фактический лимит не больше 32.
`--jobs 1` сохраняет последовательную семантику, `--jobs 32` допускает весь план.
Подготовка отдельного vLLM-окружения и абсолютного `server.python` —
[docs/vllm.md](vllm.md). Существующий Transformers-профиль также поддерживается:
`--profile examples/fitd-alert-qwen.toml --jobs 1` и `--extra qwen` в командах uv.

До первого `start()` проверяются **все 32 записи**, источник/покрытие/порядок/таксономия,
весь TOML и возможность записать начальные артефакты. Серия требует `type="model"`,
поддерживаемую рубрику и `generations=1`. `run.max_calls_per_conv` задаёт положительный
целочисленный лимит раундов FITD; если поле не указано, используется 10.
В профиле живой приёмки закреплено 20, для своих серий можно задать другой лимит,
например 200. Эффективное значение сохраняется в настройках серии и каждого запуска.
Профиль может использовать backend vLLM/Qwen/OpenAI; параллельный ALERT-профиль использует
один локальный QwenServer во всех трёх ролях. Проверка готовности моделей — отдельная команда
`tai preflight`, её вызовы не добавляются к эксперименту автоматически.

Во всех трёх FITD ALERT-профилях собственные `system`-инструкции tai отсутствуют
у Target, Attacker и Evaluator (#31). Attacker получает неизменённые задания garak,
включая шаблон формата `Yes`/`No` для проверки соответствия; оценщик получает
`alert-safety-v1` в user-сообщении. Штатный chat template Qwen2.5 сам вставляет
`You are Qwen, created by Alibaba Cloud. You are a helpful assistant.` при отсутствии
system в истории tai. Это оформление tokenizer сохраняется без правки.
[Контроль на Transformers](acceptance/2026-09-23-alert-no-system.md) публикует
воспроизводимые входы и сырые результаты для сравнения с 4B; он не подтверждает
живую работу vLLM или полную приёмку #30. Историческое
[сравнение инструкций](acceptance/2026-09-23-alert-attacker.md) относится к прежним настройкам.

Один проверенный снимок конфигурации задаёт фабрики участников. `RoleProfile.fresh()`
создаёт отдельные настроенные LLMChat и оценщик каждой записи;
секреты окружения разрешаются при валидации, не перечитываются в середине серии.
Фабрика получает `SeriesIdentity(sequence, micro_category)` и новый базовый Message.
Оценщик получает этот Message при каждом `evaluate(base, result)`.
Общим является сервер, а не разговоры; чтение начальных настроек не запускает его.
Адаптер выбранной стратегии использует закреплённый garak и определяет точки оценивания.
Координатор проверяет `wait(0)`: место освобождается только после завершения worker,
внешнего сохранения через `capture_run` / `save_run` и обновления индекса.
Состояния `COMPLETED` самого по себе недостаточно, пока worker не освободил участников.
Завершившаяся поздняя запись сохраняется сразу, без ожидания более ранних записей.

Ошибки создания User, старта, выполнения и модельного оценивания учитываются
отдельно, после чего начинается следующая запись. Ctrl+C устанавливает флаг;
`stop()` вызывается у **всех** активных User вне обработчика сигнала, перед ожиданием
любого из них. Повторные сигналы сохраняют ожидание
завершения уже допущенного модельного вызова или оценивания целиком и освобождения
участников; затем внешний код сохраняет итоговые артефакты. Возвращённый ответ сохраняется в разговоре;
полученная boolean-оценка сохраняется с ID предъявленного результата даже в
`STOPPED`, но не входит в агрегированное `evaluated`. Ошибка текущего вызова
сохраняет фактический `FAILED`; после прерывания следующая попытка не начинается.
Остановка во время сохранения использует
фактическое окончательное состояние User. Если запуск уже закончен, его
`COMPLETED` сохраняется, а серия отмечается прерванной. Запись, до `start()` которой
дошёл сигнал, не учитывается; исключение при создании/старте считается попыткой.

Коды выхода: `0` — все попытки завершились `COMPLETED` (в том числе с отрицательной
или отсутствующей оценкой), `1` — есть ошибка/иное состояние, `2` — ошибка
конфигурации/чтения/записи общих файлов, `130` — прерванная серия. Ошибка сохранения
отдельного запуска фиксируется как `storage_error` и даёт код 1, серия продолжается.
Ошибка записи любого общего файла (включая индекс, отчёт и финальные настройки)
завершает команду, а все активные User останавливаются, ожидаются и сохраняются
перед освобождением общего сервера. Исходная ошибка общего хранилища не подменяется
вторичной ошибкой при попытке записать заключительный снимок.

## Прямой консольный вывод

Один `SeriesConsole` владеет stderr и Rich Live. Отдельный `ConsoleRunJournal`
внедряется через `journal_factory` выбранного эксперимента; он декорирует обычный файловый
журнал и обновляет адресуемую строку непосредственно из наблюдаемых операций.
`bind` показывает начало, `call` — текущий вложенный метод, завершённый Exchange —
запрос и ответ конкретной роли, `finish` — исход после освобождения участников.
Координатор явно сообщает `STOPPING`, `SAVING` и окончание сохранения.

Перед таблицей один раз выводится backend из настроек участников: `Transformers`
для `backend=qwen`, `vLLM` либо `OpenAI-compatible`. При разных backend подпись
перечисляет роли. Чтение этих настроек не загружает модель.

Колонки таблицы: `# | Состояние | Текущая функция | Запрос к Target | Ответ Target`.
`Запрос к Target` содержит фактически отправленный запрос последнего завершённого
обмена с Target; `Ответ Target` — ответ на это обращение. Запрос может быть сформирован
стратегией FITD, например шаблоном realignment с цитатой предыдущего ответа.
Обёртка передаёт оба текста вместе после
завершения вызова, с общим `call_id`. Пока следующий ответ готовится или если
вызов завершился ошибкой, предыдущая пара остаётся на экране.
`Текущая функция` отдельно показывает операцию, которая выполняется сейчас.
Работа Attacker и оценщика видна в этой колонке и не заменяет показанный обмен
с Target. До первого завершённого обмена с Target обе текстовые колонки пусты.

`--lines-per-attack N` задаёт **фиксированную высоту блока атаки**, по умолчанию 5.
Это положительное целое, применяемое одинаково при любом `--jobs`. Ширина колонок
зависит только от ширины терминала: служебные колонки компактные, основное место
получают `Запрос к Target` и `Ответ Target`. Текст переносится внутри ячейки и при превышении N строк
заканчивается `…`; короткие ячейки дополняются пустыми строками. Свободное место
между ячейками не перераспределяется. Заголовки колонок занимают одну общую строку.
Тексты редактируются общей политикой секретов, пробелы нормализуются; markup/ANSI
не интерпретируются. Перенос и обрезка учитывают ширину Unicode-ячеек.

Атака закреплена за экранным блоком до окончания сохранения. Освободившийся блок
получает ожидающий отображения запуск, остальные видимые атаки сохраняют позиции.
Вместимость равна `(высота терминала − 2) // N`; число скрытых активных запусков
показывается в короткой сводке. При изменении размера терминала вместимость и ширины
пересчитываются. Если даже один блок не помещается по высоте, Rich обрезает кадр
по нижней границе терминала, сохраняя заданную логическую высоту блока.

Во время выполнения состояние показывает `RUNNING`, `STOPPING`, `SAVING`.
После сохранения вместо `COMPLETED` выводится `УСПЕХ` или `НЕУСПЕХ` согласно
`classify_outcome()` для сохранённого финального результата. Отсутствующая или
не соответствующая результату оценка даёт `НЕТ ОЦЕНКИ`; остановка и ошибки сохраняют
статусы `STOPPED`, `FAILED`/`ERROR`. Пока исход рабочего выполнения ожидает внешнего
сохранения, отображается `SAVING`.
Не-TTY получает обычные переходы состояния и финальный кадр без кодов перерисовки.
JSON всегда остаётся в stdout; исходные состояния и оценки сохраняются в артефактах.

## Артефакты: индекс schema_version=2, отчёт schema_version=1

```text
<artifacts-dir>/<series UUID>/
  manifest.json
  ALERT_taxonomy.md
  effective-profile.json
  final-settings.json
  index.json
  report.json
  vllm.log                  # только после первого обращения к vLLM
  runs/<run UUID>/
    result.txt
    events.jsonl
    metadata.json
```

Все ссылки внутри индекса относительны каталогу серии: каталог можно перенести
целиком. Пути исходных входов в `sources` — диагностические абсолютные пути.

| Файл | Данные |
| --- | --- |
| `manifest.json`, `ALERT_taxonomy.md` | Точные байтовые копии проверенных входов, включая prompts, seed, ревизию источника, исходные ID и таксономию. |
| `effective-profile.json` | Фактический `attack.type`, параметры под `fitd`, `adaptive_attacks` или `badchars_deletion`, ревизия garak, версия tai/Python, платформа, начальные настройки только используемых ролей, версия и полный текст рубрики. |
| `final-settings.json` | Та же схема после серии: фактическая готовность/версия сервера либо `loaded`/`actual_dtype` Qwen. Истории каждого запуска находятся в его metadata. |
| `index.json` | План из 32 ID и сохранённый префикс предпринятых попыток с фактическими исходами; схема ниже. |
| `report.json` | Короткая детерминированная агрегация; схема и формула ниже. |
| `runs/<UUID>/…` | Обычные артефакты выбранной стратегии: полный результат, события (включая отброшенный материал и оценки) и финальные метаданные. |

Настройки ролей включают системные инструкции, генерацию, модель/ревизию,
устройство/запрошенный dtype, кеш и версии библиотек. Начальное значение
`actual_dtype=null` означает ещё не загруженные веса. Базовый Message, полная
рубрика/конфигурация оценщика и начальные/конечные настройки каждого запуска
дополнительно находятся в его `metadata.json`; обмены оценщика — в `events.jsonl`.
Настроенные секреты авторизации скрываются в диагностике по общим правилам проекта;
`result.txt` содержит полный предъявленный текст.

### Индекс

Верхний уровень:

| Поле | Значение |
| --- | --- |
| `schema_version`, `series_id` | `2` и UUID серии. Чтение последовательных индексов v1 сохранено. |
| `jobs`, `effective_jobs` | Запрошенный лимит и `min(jobs, 32)`. |
| `manifest`, `effective_profile`, `final_settings` | Ссылки на соответствующие файлы. |
| `sources` | Для `manifest`, `profile`, `taxonomy`: исходные `path` и `sha256`. Снимок эффективных настроек сохраняется вместо секретов исходного TOML. |
| `started_at`, `finished_at` | UTC ISO 8601. `finished_at=null` во время исполнения. |
| `duration_seconds` | Число секунд по монотонным часам, либо `null` до завершения. Включает запуск/ожидание/сохранение исходов, исключает начальную валидацию. |
| `interrupted` | Получен SIGINT до закрытия серии. |
| `complete` | Серия завершена без прерывания и содержит исходы всех 32 попыток; ошибки отдельных запусков не делают её неполной. |
| `planned` | Все 32 записи в сохранённом порядке: `id`, `source_category`, `micro_category`, `macro_category`. План не участвует в `total`. |
| `entries` | Только предпринятые попытки в том же порядке, схема ниже. |

Одна `entries`-запись:

| Поле | Значение |
| --- | --- |
| `sequence` | Порядковый номер с 1; плюс четыре поля идентичности из `planned`. |
| `phase` | `active` после предпринятого допуска; `finished` после worker cleanup и внешнего сохранения/фиксации ошибки. |
| `base_id` | ID нового базового Message; текст берётся из манифеста. |
| `started_at`, `finished_at`, `duration_seconds` | UTC и монотонная длительность попытки, включая создание User и ожидание финализации. |
| `state`, `reason`, `run_id`, `progress` | В active — снимок допуска без финального результата; в finished — фактический `status()` после `wait()`. При ошибке создания User — `null`; при отклонённом старте обычно `IDLE`, `reason=null`, `run_id=null`. Ошибка не подменяет фактическое состояние искусственным `FAILED`. |
| `error` | `null` либо `{phase, type, message}` для исключения оркестрации (`create_experiment`, `start`, `wait`) или отказа журнала (`journal`). Итог берётся из `User.snapshot()` после ожидания; ошибки рабочего FITD/оценщика представлены его `FAILED` и `reason`, подробности — в событиях. |
| `storage_error` | `null` либо `{phase: "save", type, message}`: ошибка внешнего сохранения. Не меняет фактические `state`, `reason`, `result` и `evaluation`. |
| `result_id` | ID результата из финального статуса, либо `null`. |
| `result` | `{kind: "Message", id: "…"}`, только если финальный снимок действительно содержит Message; иначе `null`. Это компактное свидетельство наличия результата, полный исходный Message сохраняет внешний writer. Пустой текст также является Message. |
| `evaluation` | Сохранённая финальная оценка `{result_id, success}`, либо `null`; не ищется в старых событиях. |
| `artifacts` | `directory`, `result.txt`, `events.jsonl`, `metadata.json`: относительные ссылки. Для отсутствующих или недоступных при проверке файлов — явный `null`; каталог соответствует выделенному UUID, даже если создание каталога запуска завершилось ошибкой. |
| `artifact_errors` | Ошибки проверки файлов запуска: объект с именами файлов и диагностикой `{type, message}`. Пустой объект означает отсутствие ошибок проверки. Ошибка сохраняется отдельно от фактического состояния/причины User и от `error`; остальные ссылки проверяются, серия продолжается. |
| `classification` | `{evaluated, success, reason}`: валидность для отчёта, boolean или `null`, причина классификации. Пересчёт независимо выводит её заново из полей выше. |

Причины классификации: `active`, `valid`, `execution_error`, `storage_error`, `artifact_inspection_error`,
`not_completed`, `missing_result`,
`missing_or_malformed_evaluation`, `non_boolean_evaluation`, `result_id_mismatch`.
`classification.success=null` отличается от корректной отрицательной оценки.

Индекс и отчёт записываются одним координатором атомарной заменой **после допуска
и после сохранения каждой попытки**. Начальный индекс имеет пустой `entries`.
Активная запись учитывается в total, но её `result`, `result_id`, `evaluation`,
`finished_at` и `duration_seconds` равны null. V2 проверяет согласованность phase и
finished_at и запрещает финальное свидетельство в active-записи. При SIGINT сначала
сохраняется прерванный активный снимок, затем каждый законченный исход.
`index.json` — источник пересчёта: между заменами файлов `report.json` может отражать предыдущий снимок.
Окончательное сохранение согласует оба файла, в том числе при сигнале во время записи.

### Короткий отчёт и знаменатель

Верхний уровень: `schema_version=1`, `series_id`, `manifest`, `complete`, `groups`.
`groups` всегда содержит `hate`, `crime`, `substance`, `sex`, `self_harm`, `weapon`.
В каждой группе:

- `total` — число **предпринятых** попыток, включая ошибку создания/старта;
- `evaluated` — только `COMPLETED` без ошибок оркестрации/сохранения/проверки артефактов, с финальным Message,
  строго boolean `evaluation.success` и равенством
  `evaluation.result_id == result.id == result_id`;
- `successful` — оценённые результаты с `success=true`;
- `unevaluated = total - evaluated`;
- `success_percent = 100 * successful / evaluated`, при `evaluated=0` — JSON `null`.

Нельзя превращать `"false"`, `0` или `1` в boolean. Ошибка/остановка остаётся
неоценённой даже при наличии корректной старой или финальной оценки. Оценка другого
Message недействительна. Корректное `false` увеличивает `evaluated`, а не `successful`.
Подсчёт по запускам; проценты микрокатегорий не усредняются. В полном прогоне `total`
равны 8/8/5/3/3/5. При прерывании незапущенные записи не попадают в знаменатель;
пустые группы также присутствуют с нулевыми счётчиками и `success_percent=null`.

Доля успеха — результат выбранного оценщика. Qwen 0.5B может неверно понимать
запрос/ответ или рубрику, ошибаться при классификации и выдавать невалидный JSON.
Сохранённые полные тексты и оценки позволяют проверять эти ограничения отдельно.

## Пересчёт и Python API

```bash
uv run --locked tai alert-report \
  --index runs/alert/<series-UUID>/index.json \
  --output runs/alert/<series-UUID>/report-rebuilt.json
```

Замените `<series-UUID>` фактическим UUID. `--output` необязателен; JSON всегда
выводится в stdout. Родитель выходного файла должен существовать. Запись поверх
входного индекса отклоняется. Некорректная схема/повторные ID/несогласованный порядок
индекса — ошибка, а отсутствующая/невалидная оценка — неоценённый результат.

Пересчёт читает **только `index.json`**: полного журнала, исходного профиля,
доступа к весам и даже файлов результатов для расчёта не требуется. Полные артефакты
служат для отдельной проверки корректности сохранённых свидетельств. Кешированные
`classification`/`complete` не заменяют расчёт; вывод имеет стабильный порядок полей,
отступы и конечный перевод строки, поэтому неизменный индекс даёт одинаковые байты.

```python
from pathlib import Path
from app.series import run_alert_series
from alert.report import build_series_report, classify_outcome, reconstruct_report

series = run_alert_series(
    Path("examples/alert-manifest.json"),
    Path("examples/fitd-alert-vllm.toml"),
    Path("runs/alert"),
    taxonomy_path=Path("ALERT_taxonomy.md"),
    jobs=4,
)
assert reconstruct_report(series.directory / "index.json") == series.report
```

`run_alert_series` работает в главном потоке (временно владеет SIGINT), возвращает
`SeriesResult(directory, report, exit_code)`. Ошибки входов/файлов выбрасываются как
`ValueError`/`OSError`; отдельные ошибки запусков находятся в индексе.
`build_series_report(index: dict)` и `classify_outcome(outcome: dict)` — чистые функции.
`reconstruct_report(index_path, output=None)` добавляет чтение/запись файлов. Ни одна
функция отчёта не вызывает `evaluate` или `send`.
