# Схема новых журналов

Журнал запуска — JSONL-файл. Прозрачная обёртка дополняет каждое событие полями
`schema_id` и `schema_version`, которые сообщает конкретный журнал. Дисковый
журнал сейчас использует `tai.run` / `1`. `ParsedJournal` отклоняет неизвестную
пару или запись без неё, не пытаясь угадать прежний формат.

Каждый `AttackRun` начинает работу событием `start` с текстом базового
запроса, его происхождением (`base_metadata`) и `attack`. Значение `attack`
описывает вложенную сборку Target, оценщика и стратегии, включая настройки
моделей и `max_calls_per_conv`; сами участники выбирают публикуемые сведения
через `description()`. Поле журнала в описание атаки не входит. Дальнейшие
`call`, `step`, `decision`, `result`, `judgment` и `end` сохраняют ход запуска.

В серии первый журналируемый шаг собранной атаки — `start`. Общий
`summary.json` лежит в корне запуска и содержит только доступные внешнему
циклу данные: базовый запрос с происхождением, описание атаки, её финальный
результат либо ошибку. Ошибка до сборки атаки может не иметь журнала.
Оценки финального результата следует читать из журналов в подкаталогах атак.

Для функциональной оценки `RecordedFunctionalTest` принимает журнал через
контракт: `start(mlops)` записывает `functional_test` с
`logs_type: "generative_models_functional_test"`, а `record(task_name,
results, seconds)` записывает одно событие `dataset` с `task_name`, числовыми
`results` и `time` в секундах. Эти события не запускают бенчмарки.
