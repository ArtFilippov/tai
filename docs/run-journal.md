# Независимый журнал запуска (#20)

`FITDUser` выполняет стратегию. `FITDExperiment` собирает его с обёртками методов
и новым `RunJournal` для каждого допуска запуска. Журнал формирует и хранит события
и диагностические снимки настроек. `result.txt` и `metadata.json` записывает
[внешний модуль сохранения](result-storage.md) после ожидания User.

`AdaptiveAttacksUser` / `AdaptiveAttacksExperiment` используют тот же механизм:
`attacks.shared.experiment` собирает общий `Execution` и наблюдение его операций.
Сборка FITD дополнительно оборачивает нативные решения в `attacks.fitd.observation`.
Для Adaptive Attacks журнал получает сбросы, обмены, публикации и оценки напрямую
из общего выполнения. Политика стратегии — [adaptive-attacks.md](adaptive-attacks.md).

## Python interface

```python
from tai import FITDExperiment, capture_run, save_run

experiment = FITDExperiment(target, attacker, base, evaluator, journal_dir="runs")
experiment.start()
journal = experiment.journal

cursor = 0
while not journal.wait(0.05):
    for event in journal.events(after=cursor):
        cursor = event.sequence
        print(event.dump())

# Прочитать остаток, даже если рабочее выполнение закончилось до первого опроса.
for event in journal.events(after=cursor):
    print(event.dump())
experiment.wait()  # также дождаться выхода самого потока перед следующим start()
record = capture_run(experiment, journal=journal)
save_run(record, "runs")
result, status = record.snapshot.result, record.snapshot.status
if journal.error is not None:
    raise journal.error
```

`events(after)` возвращает кортеж неизменяемых `RunEvent`; `data` каждый раз
возвращает отделённый снимок. `journal.finished` и `journal.wait()` обозначают
окончание работы и закрытие журнала после освобождения участников. Для завершения
записи не требуется вызов `User.wait()`. Сохранённая ссылка `journal` после нового
`experiment.start()` продолжает читать прежний запуск; `experiment.journals`
содержит все допущенные запуски в порядке допуска. `User.events()` удалён.
Без `journal_dir` журнал работает в памяти. `settings()` и `final_settings()`
возвращают отделённые снимки, либо `None`, если соответствующая граница не достигнута.

## Как подключены обёртки

Фабрика `journal_factory` принимает настройки журнала и возвращает объект
контракта `Journal`. Default — `RunJournal`. Серия ALERT внедряет
`ConsoleRunJournal(row, ...)`: декоратор сохраняет файловый журнал и направляет
диагностические копии в Domain-порт `ConsoleRow`. Реализация Rich находится в
Interface (`app.series_console`), соединение — в Bootstrap (`app.series`).

`bind(run_id)` отличает допущенный запуск от предварительного idle execution.
Вход `call()` непосредственно показывает наблюдаемый метод и запрос, возврат
Exchange обновляет ответ той же роли и `call_id`; контекстный менеджер восстанавливает
внешний метод при вложенности и исключении. Attacker и Target имеют отдельные пары,
оценщик их не затирает. `finish(WorkerOutcome)` очищает стек после освобождения
участников. Остановка и сохранение явно сообщаются координатором. Тексты проходят
общую редактуру до передачи в дисплей. Ошибка вывода закрывает допуск последующей
работы; ошибка отрисовки при раскрутке стека не заменяет исходное исключение метода.
Обычный `events(after)` остаётся интерфейсом чтения доказательств, но консоль серии
его не опрашивает и не восстанавливает из него состояние.

`attacks.fitd.experiment` использует сборку из `attacks.fitd.observation`: локальные
подклассы `FITDProbe`, `FITDTarget` и `ObservedExecution` создаются до конструирования
рабочих объектов. Поэтому `self.save()` в конструкторе `FITDTarget` и вызовы внутри
составных операций проходят через обёртки. Внутренний `_NativeFITD(FITD)` направляет
проверки и выбор продолжения через порт операций на тот же фасад `FITDProbe`;
его библиотечные hooks сохраняются и в наблюдаемом, и в необёрнутом режиме.
Из `Continuation` читается только явное поле `decision`; проверки библиотеки,
индексирование лестницы и выбор ветки остаются в адаптере. Необёрнутый `FITDUser`
использует те же рабочие методы.

Обёртки передают журналу только входы, результаты и исключения из
[контрактов операций](fitd-operations.md). Журнал не читает приватные поля стратегии,
не выводит решение из текста и не вызывает модель или оценщик.

`EvaluatorSetup` собирает оценщик и его диагностические зависимости до запуска.
Обёртки исходного чата получают корреляцию только на время наблюдаемого
`evaluate(base, result)`. User не извлекает чат из оценщика и не меняет его ввод-вывод.
Контекст наблюдения локален потоку и восстанавливается также после ошибки;
повторные и параллельные независимые запуски не смешивают записи.

## Записи и связи

- `run_started` фиксирует допуск до старта потока. `run_configured` содержит
  настройки после начальных сбросов, не историю предыдущего запуска.
- `call_started` / `call_completed` / `call_failed` / `call_cancelled` связаны
  `call_id`; `context` содержит запуск, роль, разговор, попытку и причину.
  Обращение оценщика дополнительно содержит `result_id` и `evaluation_id`;
  начало также содержит `base_id` и диагностические настройки разговора.
- `checkpoint_captured`, `checkpoint_created` и `target_exchange` связывают обмен
  с контрольной точкой и конкретными Message. Непрозрачные токены не сериализуются.
- `local_decision` содержит фактический результат нативной проверки, а для
  alignment — обмен Attacker с суждением. `branch_selected` содержит следующую
  попытку и её Message, даже если лимит или оценка не позволят её отправить.
- `history_reset` / `history_restored` и `conversation_synchronized` сохраняют
  причину и точки до/после изменения. Включены сбросы при инициализации.
- `result_published.change` — `accepted` или `replaced`; `result_withdrawn` и
  `result_unchanged` отражают остальные исходы. Сохраняются прежний/новый Message,
  прежняя/новая оценка, точка и причина. Выбор `continue` ещё не означает принятия:
  остановка может закрыть допуск между решением и публикацией.
- `evaluation_started` / `evaluation_completed` связывают оценку с точным
  предъявленным Message, причиной и контрольной точкой. `evaluation_id` идентифицирует
  конкретный вызов, `base_id` и `result_id` — точную пару; начало содержит снимки
  `base` и `result`. Ошибки/отмены сохраняют ту же корреляцию.
- `operation_started` фиксирует вход в остальные наблюдаемые методы;
  `resources_released` и единственное `run_finished` завершают нормальный журнал.

Начальное событие и `stop_requested` можно читать ещё до их сохранения: управляющий
поток только добавляет снимок в память. Все записи на диск выполняет рабочий поток
перед следующей операцией. `run_finished` появляется после фиксации исхода и
освобождения участников. Итоговые файлы результата в рабочем потоке не записываются.

## Fail fast и диагностические копии

При ошибке записи до операции она не выполняется. При ошибке записи после возврата
операции уже сделанная работа сохраняется, но новая не допускается. Журнал хранит
первоначальный объект исключения в `error` и отклоняет все дальнейшие записи тем
же исключением, включая случай, когда garak или модельный оценщик перехватил его.
Нет повторов, фонового восстановления или резервного хранилища. Освобождение
участников и закрытие файла выполняются всегда; вторичная ошибка закрытия не
подменяет первоначальную. CLI и серия получают неуспешный исход.

При отказе хранилища файлы могут быть неполными, а хвост событий существовать только
в памяти. Ошибку следует читать из `journal.error`, а не пытаться восстановить
успешный исход по частичному журналу. Внешний writer всё равно может сохранить
фактический `User.snapshot()` после ожидания, включая `FAILED` и доступный результат.

Сборка объединяет настроенные секреты Target, Attacker и модельного оценщика.
Журнал применяет существующую редактуру к копиям, включая JSON-экранированные
значения, ключи, provenance и оболочку события. Исходные Message, вход оценщика и
`result.txt` не изменяются. Результат никогда не восстанавливается из снимка.

CLI читает `journal.status()` и события непосредственно; окончательный исход CLI
и серии поступает из `User.snapshot()`. Preflight использует
тот же журнал для реальных обменов и модельного оценивания, включая безопасное
форматирование отчёта. Офлайн-проверки: `tests/test_journal.py` и существующие
сквозные тесты FITD, остановки, provenance, трёх ролей и серии.
