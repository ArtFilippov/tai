# Проверка публичного режима Zen перед #9

**Дата:** 2026-09-14, UTC. **Обновлённый итог:** с предоставленным пользователем
ключом и заголовком `x-opencode-session` обе роли получили HTTP 200 и `READY`.
Доступ к генерации подтверждён отдельной HTTP-проверкой. В `OpenAIChat` ещё нужно
добавить передачу сессионного заголовка; живой FITD для #9 не запускался.

## Условия первоначальной проверки

- База рабочего дерева: `b4740c2c8b4cad1f652eca546b186b4b28b68812`.
- Python 3.12.14, существующее окружение `.venv`.
- Endpoint: `https://opencode.ai/zen/v1/chat/completions`.
- Target / Attacker: `big-pickle` / `big-pickle`.
- Авторизация: явно заданный `api_key = "public"`, то есть `Bearer public`.
  `public` — публичное значение из реализации OpenCode, личные ключи не использовались.
- Системные инструкции, температуры, `max_tokens=512`, `timeout=120` — из
  `examples/fitd.toml`; транспорт добавляет `n=1`, `stream=false`.
- Контрольный запрос каждой роли: `Reply with exactly READY.`.
- Два независимых `OpenAIChat`, прямой HTTP без прокси и перенаправлений.

[Документация Zen](https://opencode.ai/docs/zen/) указывает бесплатную цену Big Pickle.
В [реализации провайдера OpenCode](https://github.com/anomalyco/opencode/blob/dev/packages/opencode/src/provider/provider.ts)
при отсутствии личной авторизации выбираются бесплатные модели и `apiKey: "public"`.
Это основание проверить публичный режим, но не доказательство его работоспособности
в отдельном приложении.

## Наблюдения

### 1. Публичный ключ со стандартным User-Agent Python

В `2026-09-14T19:56:09.120085+00:00` обе роли через публичный `OpenAIChat.send()`
получили одинаковую ошибку:

```text
OpenAIAuthenticationError: Chat Completions HTTP request rejected (HTTP 403); response_bytes=0
```

Минимальный запрос через `urllib` с тем же endpoint и авторизацией, без системных
инструкций и с `max_tokens=32`, повторил 403. Его тело, полученное отдельно от
транспорта приложения, установило источник отказа:

```json
{
  "status": 403,
  "error_code": 1010,
  "error_name": "browser_signature_banned",
  "detail": "The site owner has blocked access based on your browser's signature.",
  "what_you_should_do": "**Do not retry.** Your user-agent has been banned by the site owner."
}
```

Заголовок `Server: cloudflare`, Ray ID `a3b1f4c33ccf9828-PHL`, время в теле ответа
`2026-09-14T19:56:38Z`. Нулевой `response_bytes` в ошибке приложения не означает,
что провайдер прислал пустое тело: транспорт намеренно не копирует тела HTTP-ошибок.

### 2. Изменение только User-Agent

В минимальном запросе заменён только User-Agent на `tai/0.1.0`.
Cloudflare больше не вернул 1010; получен HTTP 400 и следующий ответ Zen:

```json
{
  "type": "error",
  "error": {
    "type": "MissingSessionID",
    "message": "Error from provider (Console): OpenCode's free tier can only be used in OpenCode"
  }
}
```

Ray ID: `a3b1f54b6a0922ad-PIT`. Запрос не получил ответа модели.

### 3. Повтор обеих ролей через исправленный транспорт tai

Транспорт теперь явно указывает `User-Agent: tai/<версия установленного пакета>`.
В `2026-09-14T19:58:52.514268+00:00` повторена исходная проверка обеих ролей
с полными настройками примера:

```text
Target:   OpenAIHTTPError: Chat Completions HTTP request rejected (HTTP 400); response_bytes=0
Attacker: OpenAIHTTPError: Chat Completions HTTP request rejected (HTTP 400); response_bytes=0
```

Это подтверждает устранение исходного 403 для этих запросов, но обе проверки
генерации остались отрицательными. Тело `MissingSessionID` наблюдалось в отдельном
минимальном запросе; приложение по-прежнему не публикует тела HTTP-ошибок.

### 4. Предоставленный ключ и сессионный заголовок

Пользователь предоставил `OPENCODE_ZEN_KEY.json` с ключом в `opencode.key` и
`opencode.type = "api"`. Файл исключён из Git пользовательским правилом
`.gitignore`. Значение ключа загружалось только в память процесса и не включалось
в команды, отчёт или вывод. Исходные настройки ролей взяты из того же TOML;
публичное значение авторизации заменялось ключом только в памяти.

В `2026-09-14T20:10:30.139254+00:00` обе роли через текущий `OpenAIChat`
получили HTTP 400. Отдельный диагностический запрос в `20:11:05 UTC` с ключом
повторил `MissingSessionID` и прежний текст о бесплатном тарифе.

В [документации OpenCode Go](https://opencode.ai/docs/go/#where-can-i-use-it)
для сторонних клиентов указаны собственный User-Agent и стабильный ID разговора
в `x-opencode-session`. Это документация Go, поэтому применимость к Zen проверена
отдельным реальным запросом, а не принята на веру.

В `2026-09-14T20:12:15.231069+00:00` выполнены два прямых HTTP-запроса через
`urllib`, с теми же настройками, ключом и `User-Agent: tai/0.1.0`. Единственное
добавление — `x-opencode-session` с отдельным новым UUID для каждой роли.

| Роль | HTTP | Полный ответ | finish_reason | Время |
| --- | --- | --- | --- | --- |
| Target | 200 | `READY` | `stop` | 1.28 с |
| Attacker | 200 | `READY` | `stop` | 1.37 с |

ID диагностических разговоров:

- Target: `9ba419f8-92f0-413c-8bb8-17bd9746ff23`;
- Attacker: `2f07a3b8-d6d1-4ee8-b45e-3036b88e69bc`.

Это ID разговоров HTTP-проверки, не UUID запуска FITD. Проверка завершена
в `2026-09-14T20:12:16.606685+00:00`. Контрольный запрос — прежний
`Reply with exactly READY.`; никаких дополнительных платных моделей не вызывалось.

**Вывод:** с предоставленным ключом прямой API `big-pickle` работает, если передан
сессионный заголовок. Предыдущее сообщение `MissingSessionID` не доказывало запрет
такой интеграции. Публичный ключ вместе с сессионным заголовком здесь не проверялся.

- В `examples/fitd.toml` обе роли явно используют публичное значение; отсутствие
  переменных личных ключей больше не останавливает загрузку этого примера.

## Граница готовности

`FITDUser.start()` и `tai fitd` для живого эксперимента не вызывались. UUID,
результат, оценка и артефакты живого запуска отсутствуют. Эта проверка подключения
не является приёмкой #9.

Внешний доступ с предоставленным ключом подтверждён для обеих ролей. Для готовности
приложения к #9 остаётся добавить в `OpenAIChat` поддержку сессионного заголовка
со стабильным ID разговора, явно подключить ключ к конфигурации запуска и повторить
проверку через этот транспорт. Текущий `OpenAIChat` без заголовка всё ещё получает
HTTP 400. Успешные отдельные HTTP-запросы не заменяют живую приёмку FITD.

Вся оставшаяся подготовка оформлена в
[#11 — «Подготовить Target и Attacker к прямому API Zen перед #9»](https://github.com/ArtFilippov/tai/issues/11).
У тикета нет открытых блокеров; он является блокирующей зависимостью #9.
Его граница завершения — подтверждённая готовность приложения к живой приёмке,
без выполнения самого живого FITD.
