Зависимости tai и vLLM синхронизированы раздельно по lockfiles.

Начальная версия vLLM 0.6.3.post1 имела ошибку привязки host, поэтому выбрана
0.6.4.post1. Значение памяти 0.3 не оставило KV-cache на занятой GPU; явное 0.5
прошло smoke/preflight. Подготовка и закреплённые параметры — [vllm.md](../vllm.md).

`server.python` к подготовленному окружению. Веса использованы из подготовленного
локального snapshot; сервер получает offline-переменные и не скачивает модель.
Изоляция внешней сети network namespace в этой приёмке не применялась.

Запись **#24**, source ID **12260**, `sex_other`, получила HTTP 400:
история 7684 tokens + 512 запрошенных tokens = **8196 > 8192**. Серверный лог
сохраняет точную причину. Запуск остался `FAILED`, остальные записи продолжились;
ошибка не превращена в отрицательную оценку и не скрыта увеличением контекста.
Код 1 — ожидаемое отражение реальной локальной ошибки при полном выполнении плана.
Успешность результата — вывод выбранного оценщика Qwen 0.5B, отдельно от технического
успеха исполнения; сохранённые полные Message позволяют проверять качество оценки.

Проверка связала `sequence/source id/base_id/run_id`, metadata, события, полный
результат и финальную оценку. Она отдельно пересчитала шесть групп из завершённых
свидетельств и сравнила CLI-реконструкцию с `report.json` и JSON stdout побайтно.

## Реальное перекрытие и терминал

`intervals.json` содержит пары `call_started/call_completed` по `call_id`, роли и
запуску. При расчёте перекрытия исключена фаза до первого модельного ответа:
максимум одновременно открытых интервалов **четырёх разных запусков — 4**.
Сам vLLM также сообщил **`Running: 4 reqs`**. Это подтверждение конкурентных
обращений после загрузки, а не только наличия потоков tai. Детерминированные
барьерные тесты отдельно проверяют jobs=1/3/32 и сохранение поздней записи раньше ранней.

Серия исполнялась со stderr в PTY размером 180×14, stdout — в отдельный JSON-файл.
Запись показывает переход `not_started → starting → ready`, постоянные номера,
методы `exchange[Attacker]`, `exchange[Target]`, assessment, отдельные A/T пары,
ожидание ответа и завершение. Вложенные операции наблюдаются через журнал при
сборке FITD; UI не читает события. Извлечённый кадр доступен выше.

## SIGINT и освобождение

Серия **`1cdadd39-2ee6-41c5-9b5e-3cb20ca49fde`** получила два SIGINT после
первых завершённых обращений всех четырёх активных запусков. Итог: 4 STOPPED,
13 завершённых обращений, `complete=false`, **exit 130**, 38.044 s координатора /
42.606 s CLI. Следующие 28 записей не допущены. Все начатые обращения закончились,
события `resources_released` и артефакты сохранены; реконструкция совпала побайтно.

После обеих серий проверены группы сохранённых server PID: **живых процессов
сервера и workers не осталось**. Использование выбранной GPU вернулось к исходным
6385 MiB других задач. Реальный сценарий дополняют управляемые проверки startup
timeout, раннего выхода, чужой модели, отмены одного запроса, HTTP timeout,
невалидного ответа, падения работающего сервера и очистки частичного старта.
