# tai — эксперименты с устойчивостью LLM

Система выполняет стратегии атак на языковые модели и отдельно оценивает
предъявленный ими текст. Общий контракт — `Message` на входе и `Message` на выходе;
журнал запуска сохраняет ход эксперимента отдельно от результата.

Реализован первый вертикальный срез [тикета #2](https://github.com/ArtFilippov/tai/issues/2):
неблокирующий `FITDUser`, настоящий алгоритм FITD из garak, независимые разговоры
Target и Attacker, детерминированный оценщик и артефакты запуска.
Термины и архитектурные решения: [CONTEXT.md](CONTEXT.md), [docs/adr](docs/adr).

## Установка и офлайн-проверки

Нужны Git и [uv](https://docs.astral.sh/uv/). uv выбирает Python 3.12 по
`.python-version`; системный Python менять не требуется.

```bash
uv sync --locked
uv run --locked pytest
uv run --locked ruff check .
uv run --locked ruff format --check .
uv run --locked mypy
uv run --locked python examples/offline_fitd.py
```

Первой установке нужна сеть для Python и зависимостей. Сами тесты и пример
работают без моделей, сети и учётных данных. Тесты запрещают сетевые соединения
и управляют только ответами моделей: построение лестницы, переходы FITD и
решение о продолжении выполняет настоящая библиотека.

### Закрепление garak

`uv.lock` закрепляет зависимости, а `tool.uv.sources` — garak на коммите
`3f50ea5ff9cd7050099940647c15c39b07a93392`. Соседний checkout не используется.

В `tool.uv.dependency-metadata` явно задан минимальный профиль зависимостей
приватной текстовой интеграции FITD: Colorama, tqdm, PyYAML и xdg-base-dirs.
Исходный пакет garak устанавливается целиком с этого коммита, но его обязательные
зависимости для всех провайдеров и GPU-инференса заменены этим профилем при
разрешении зависимостей uv. Профиль поддерживает именно интеграцию tai;
произвольные плагины и CLI garak могут требовать дополнительные зависимости.
Для воспроизводимой установки используйте `uv sync --locked`, а не `pip install .`.

## Публичный Python API

Все публичные типы доступны из `tai`; типы garak скрыты в `tai/_fitd.py`.

- `Message(text)` — неизменяемый текст с уникальным `id`, методами `base()`,
  `to_string()` и JSON-снимком `dump()`.
- `LLMChat(generate, model="…", system="…")` — владелец истории. Синхронный
  `send(Message)` передаёт функции `generate` неизменяемый кортеж `ChatTurn`
  с ролями и полным контекстом; функция возвращает строку. В историю попадает
  только завершённый обмен. `history()` возвращает неизменяемый снимок.
- `FITDUser(target, attacker, base, evaluator, artifacts_dir="runs")` — исполнитель
  одного запуска. Роли требуют разных экземпляров `LLMChat`, даже для одной модели.
- `start()` возвращает `None` и запускает рабочий поток; `status()`, `result()`
  и `events(after=0)` доступны во время генерации. `after` — номер последнего
  прочитанного события (нумерация начинается с 1). `wait(timeout)` — необязательное
  блокирующее ожидание завершения рабочего выполнения и записи артефактов.
- `ContainsTextEvaluator(criterion)` ищет непустую строку с учётом регистра
  только в `result.to_string()`. Методы `is_success`, `reason` и `evidence`
  независимы. Собственный `Evaluator` может реализовать только нужные методы;
  неподдерживаемые по умолчанию вызывают `NotImplementedError`.

Пример с управляемыми ответами: [examples/offline_fitd.py](examples/offline_fitd.py).
Для своего транспорта передайте две функции генерации в два `LLMChat`.
Они получают `turn.role` и `turn.message.to_string()` и выполняются в рабочем
потоке User. Методы наблюдения не вызывают генератор или оценщик.

### Результат, состояние и оценка

В этом срезе политика FITDUser — предъявлять последний завершённый ответ Target
текущего разговора. Общий интерфейс User не навязывает эту политику другим стратегиям.
Именно опубликованный `Message` целиком получает оценщик в библиотечной точке
проверки последнего уровня FITD. Положительная оценка завершает стратегию досрочно;
отрицательная позволяет продолжить. Внутренние проверки соответствия ответа
запросу проходят через Attacker; дополнительная модель оценки не подключается.

`UserStatus` — неизменяемый снимок: `state`, `run_id`, `progress`, `reason`,
`result_id`, `evaluation`. Оценка содержит идентификатор результата и `success`.
При публикации нового результата старая оценка сбрасывается в `None`.
`COMPLETED` означает штатное завершение, а не обязательно успех атаки.

Начальный профиль: одна задача, `generations=1`, три промежуточных уровня,
`max_calls_per_conv=10`. Последнее — лимит библиотечных раундов, а не общий бюджет
обращений: построение лестницы и внутренние проверки требуют отдельных вызовов
Attacker. `progress.target_calls` и `progress.attacker_calls` считают завершённые
обращения соответствующих ролей.

### Артефакты и события

Каждый запуск получает UUID и каталог `artifacts_dir/<run_id>/`:

- `events.jsonl` — дополняемый и сбрасываемый на диск после каждого события журнал.
  Начало и завершение вызовов связаны `call_id`; есть роли, входы, ответы,
  публикации, оценки и завершение запуска. Тот же поток доступен через `events()`.
- `result.txt` — полный предъявленный текст; файл существует и для пустого Message.
  Если результата ещё не было, файл отсутствует.
- `metadata.json` — итоговое состояние, прогресс, причина завершения, результат
  или `null`, его оценка или `null`, профиль FITD и начальные настройки разговоров.

`run_finished` завершает журнал, а терминальный `status()` публикуется после записи
итоговых артефактов. Вызовы `reason()` и `evidence()` автоматически не выполняются.

## Следующие срезы

Реализованный путь поддерживает продвижение по лестнице и уточнение ответа
(realignment). Откат после отказа требует согласования контрольных точек из
[#5](https://github.com/ArtFilippov/tai/issues/5); сейчас такой переход явно
завершается ошибкой интеграции. Остановка, полный контракт происхождения Message,
повторные запуски одного User, HTTP, команда `tai fitd` и живая приёмка описаны
в [#3–#9](https://github.com/ArtFilippov/tai/issues/1). Пока один экземпляр FITDUser
запускается один раз; повторный `start()` явно отклоняется.

Первое реальное подключение по общей спецификации — прямой OpenAI-совместимый API.
Qwen и локальный CPU-инференс остаются дальнейшим направлением проекта.
