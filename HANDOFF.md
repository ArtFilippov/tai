# Handoff: Python Quality, FITD и граница с garak

Обновлено: 2026-09-21, после обсуждения альтернатив интеграции FITD.
Документ фиксирует состояние кода, решения пользователя и ещё не выбранные варианты.

## Главное для продолжения

**Пользователь уточнил архитектурное требование: «Мы должны были абстрагироваться
от garak, а не наследоваться от него».** Продолжение должно устранять наследование
классов приложения от garak и зависимость наших контрактов от устройства библиотеки.
Скрыть подкласс за фасадом или добавить исключение линтера недостаточно.

Текущий `_NativeFITD(FITD)` этому требованию не соответствует. Предложение добавить
`garak.probes.base.Probe` в `ignored-parents` снято; разрешение на него не получено.

**Garak не редактируем. Окончательная архитектура пока не выбрана.** Пользователь
сначала предложил работать с неизменным `FITD` как с чёрным ящиком, затем изменил
направление: спуститься на более низкий уровень ради контроля хода атаки, оборачивая
используемые инструменты garak в наши интерфейсы. После объяснения, что в исследованной
ревизии это потребует собственной реализации подготовки и переходов FITD в tai,
пользователь ответил: **«Я пока не определился. Обнови HANDOFF, запиши туда все
предложенные альтернативы и открытый вопрос»**.

**Открытый вопрос:** допустим ли перенос подготовки лестницы и адаптивных переходов
FITD в tai с использованием детектора и ресурсов garak за нашими интерфейсами?
Это уже собственная реализация стратегии, а не исполнение `garak.FITD`.
Не считать последнее направление разрешением на такой перенос. Все альтернативы,
их компромиссы и статусы собраны в разделе 6.

Последнее поручение — только обновление этого handoff. Обсуждение и исследования
в этой сессии были read-only; исходники, зависимости и конфигурации не менялись.
Runtime-тесты и Python Quality заново не запускались.

## 1. Задача и ограничения пользователя

- Исходная задача: довести весь **Python Quality** до зелёного результата.
- Работать в субагентах, распараллеливая независимые участки с небольшими накладными
  расходами. В последней сессии субагенты только исследовали код и варианты границы.
  До продолжения снова проверить фактическое состояние файлов.
- **Полный набор runtime-тестов не запускать**: пользователь явно отложил исправление
  runtime-багов. Это не отменяет итоговую статическую проверку.
- Сохранять согласованные численные лимиты и не скрывать диагностики исключением файлов,
  blanket `Any`, подавлениями или baseline.
- Пользователь отдельно разрешил исключить стандартные базы исключений, Protocol
  и Enum из подсчёта предков, сохранив `max_parents = 3`.
- Garak не редактировать; патч/fork зависимости не согласован и противоречит
  последнему явно сохранённому ограничению. Смена закреплённой ревизии также
  не разрешена. Варианты ниже не являются поручением обновить зависимость.
- Последний коммит: **`3eb2837` — `refactor modules and contracts for Python Quality`**.
  Он уже содержит большой рефакторинг, фасад `probe.py` и первоначальный handoff.
  `7a9728a` — предыдущий коммит с согласованными лимитами. Старое утверждение об

  `git status --short` и diff были пустыми. Текущее изменение сессии — этот документ.

## 2. Найденные проблемы FITD и контрактов

### 2.1. Интеграция всё ещё основана на наследовании garak

В текущем [src/attacks/fitd/probe.py](src/attacks/fitd/probe.py):

```python
class _NativeFITD(FITD):
    ...

class FITDProbe(ProbeOperations[Conversation, Attempt]):
    # Внутри создаёт _NativeFITD(..., operations=self).
    ...
```

Фасад вошёл в `3eb2837`, но архитектурное исправление не завершено. Он отделяет публичные методы,
но сохраняет основную связь: 13 переопределений библиотечных методов, обращения
к библиотечному состоянию и вызовы `super()`. Имена и порядок вызова приватных hooks
garak остаются частью реализации приложения.

До этого фасада класс прямо наследовал `FITD` и `ProbeOperations`. В исходном
закоммиченном варианте аналогичную роль выполнял `_FITD(FITD)` в `garak_adapter.py`.
Проблема существовала до последнего разбиения файлов; новый фасад её не устранил.

### 2.2. Унаследованный публичный API выходил за пределы нашего контракта

В последнем полном отчёте `W9201` отмечал четыре метода старого `FITDProbe`:

| Метод garak | Почему он не относится к нашему Domain-контракту |
| --- | --- |
| `set_up_attack_gen_llm()` | Создание библиотечного клиента через загрузчик плагинов. |
| `set_up_detector()` | Настройка библиотечного детектора. |
| `set_up_refusal_detector()` | Настройка библиотечного детектора отказов. |
| `probe(generator)` | Общий библиотечный процесс выполнения с нативными объектами. |

`ProbeOperations` уже был реализован. Существенная часть сообщений — **«not in
Protocol»**, а не отсутствие протокола вообще. Проверка учитывает и унаследованные
методы, поэтому позиции сообщений указывали на `.venv/.../garak/probes/`.

Добавление этих методов в Domain только ради линтера расширило бы наш контракт
деталями garak. Фасад с композицией способен закрыть публичный API, однако отдельное
требование пользователя — устранить и внутреннее наследование от garak.

### 2.3. Контракты местами повторяют устройство библиотеки

В [contracts.py](src/attacks/fitd/contracts.py) появились:

- `Continuation[Attempt]`;
- `ProbeOperations[Prompt, Attempt]`;
- `TargetOperations[Prompt, Response]`.

Прямых импортов garak в этом Domain-модуле нет, но конкретные реализации подставляют
`garak.attempt.Conversation`, `garak.attempt.Attempt`, `garak.attempt.Message` и повторяют библиотечные
операции. Generic-параметры сами по себе не доказывают независимость контракта.
Нативное продолжение следует держать внутри адаптера; наружу передавать наши
результаты операций, например `BranchDecision`, `LocalDecision`, `TargetExchange`.

Уже есть полезная независимая граница: `StrategyRuntime`, `StrategyPorts` и
`ConversationPorts`. [execution.py](src/attacks/fitd/execution.py) вызывает runtime
через этот контракт, а [bootstrap.py](src/attacks/fitd/bootstrap.py) выбирает реализацию.
Эту часть можно использовать как основу дальнейшего разделения.

### 2.4. Наблюдение зависит от конкретных классов

[observation.py](src/attacks/fitd/observation.py) создаёт динамические подклассы через
`type("Observed" + base.__name__, (base,), ...)`, оборачивая именованные методы
`FITDProbe`, `FITDTarget` и выполнения. Это привязывает наблюдение к конкретной форме
реализации и её внутреннему dispatch.

При переходе на композицию нужны явные наблюдаемые операции. Обёртки должны получать
фактические входы, результаты и исключения; читать приватное состояние стратегии
или повторять решение для восстановления журнала нельзя. Нынешний механизм описан
в [docs/run-journal.md](docs/run-journal.md); смена механизма требует обновления документа.

### 2.5. Ограничение предков выявило связь с библиотечным каркасом

В последнем полном прогоне старый `FITDProbe` получал `R0901: 5/3`:

```text
FITDProbe
├── FITD
│   └── IterativeProbe
│       └── Probe
│           └── Configurable
└── ProbeOperations
    └── Protocol  # уже исключён из подсчёта
```

Пять учитываемых предков — четыре библиотечных и один проектный. Это эвристика
сложности, не доказательство runtime-ошибки. После выделения фасада библиотечная
цепочка остаётся у `_NativeFITD`; старое число `5/3` нельзя выдавать за результат
свежей проверки нового класса. Изменение подсчёта не решает требование об абстракции.

## 3. Что мешает простой композиции с закреплённым garak

Ревизия в `pyproject.toml`:
`3f50ea5ff9cd7050099940647c15c39b07a93392`.

Ниже — результаты чтения установленного кода этой ревизии, а не нового runtime-прогона.
Пути `garak/...` указаны относительно установленного пакета.

| Ограничение библиотеки | Связь с контрактом tai / подтверждение |
| --- | --- |
| `_create_init_attempts()` выбирает случайные задачи HarmBench и перезаписывает `target_prompts`. | У нас базовый запрос передаётся как явный `Message`. Простое присваивание `target_prompts` до `probe()` не помогает. `garak/probes/fitd.py:236–281`. |
| Конструктор получает language providers через глобальную службу. | Назначение локального провайдера после конструктора не устраняет эту зависимость. `garak/probes/base.py:121–158`. |
| Цикл использует глобальные buffs и `_config.transient.reportfile`. | Локальный `config_root` не изолирует все службы запуска. `garak/probes/base.py:321–381, 806–807`. |
| Проверка завершения выполняется до выбора адаптивного продолжения. | Оценка tai должна относиться к уже принятому результату после решения стратегии. Подстановка нашего оценщика в обычный detector меняет семантику. `garak/probes/base.py:836–843`, `garak/probes/fitd.py:499–570`. |
| Checks и выбор ветки вызываются через `self` без регистрации callbacks. | Внешний фасад не перехватывает внутренние вызовы. Обёртка модельного I/O не получает фактическое boolean-решение и завершённый выбор ветки. `garak/probes/fitd.py:164–184, 339–358, 366–497`. |
| Target generator получает `Conversation`, но не полный `Attempt`. | Теряются UUID попытки и связь с точным подготовленным `Message`, сейчас задаваемые перед `_execute_attempt()`. `garak/probes/base.py:309–319`; наш `target.py`. |
| Исключение Attacker оборачивается в `GarakException`, а цикл может его поглотить. | Внешняя обёртка `probe()` не восстановит исходную ошибку/остановку, если она не сохранена на внутренней границе. `garak/probes/fitd.py:147–154`, `garak/probes/base.py:831–834`. |

**Часть композиции возможна:** Target передаётся в `probe(generator)` структурно;
Attacker и детекторы используются через объектные поля `red_team_model`,
`refusal_detector`, `detector`. Подклассы garak для самого модельного I/O не обязательны.
Но этих точек недостаточно для всего перечисленного поведения. Методы `set_up_*`
не принимают готовые зависимости: они создают их через загрузчик плагинов.

Не выдавать перепривязку методов через `MethodType`, внедрение приватных методов
через configuration или временную подмену глобальных служб за поддерживаемый
композиционный API. Это сохраняет зависимость от hooks и противоречит направлению
исправления. Публичное имя `generate_next_turn_attempt()` также не делает его
самодостаточным engine API: ему нужны подготовленная лестница, native notes и службы.

## 4. Действующие контракты и обязательства

Источники требований: [CONTEXT.md](CONTEXT.md),
[ADR 0001](docs/adr/0001-textual-attack-contract.md),
[ADR 0002](docs/adr/0002-dialogue-owned-by-llm-chat.md),
[ADR 0003](docs/adr/0003-local-qwen-for-live-acceptance.md),
[наблюдаемые операции FITD](docs/fitd-operations.md).

Это требования нынешней интеграции, а не обещание, что любой вариант из раздела 6
может сохранить их все. При обсуждении чёрного ящика предлагалось пересмотреть часть
контрактов; окончательно такие изменения не приняты. При собственной стратегии
потребуется уточнить обязательство библиотечного исполнения, сохранив согласованную
прикладную семантику. До выбора варианта автоматически не отменять требования ниже.

1. **Историей и валидностью checkpoint владеет LLMChat.** Адаптер только сопоставляет
   библиотечные префиксы с непрозрачными токенами. Target и Attacker независимы.
2. **Завершённый обмен и предъявленный результат различаются.** Отказ или материал
   realignment не заменяет принятый результат автоматически.
3. **Оценщик получает точную пару `evaluate(base, result)`.** Оценивание следует за
   принятием результата; ошибка не превращается в `success=False`.
4. **Каждая нативная проверка и выбор продолжения выполняются один раз.** Наблюдение
   не пересчитывает решение и не выводит его из шаблона промпта/логов.
5. **Сохраняется идентичность Message.** Подготовленный `next_request` при отправке
   используется как тот же объект; совпадения строк недостаточно.
6. **Выбранное продолжение наблюдаемо, даже если не отправлено.** Согласование
   разговора выполняется и на последнем разрешённом раунде. Перенос согласования
   исключительно в следующий `generate()` нарушает этот контракт.
7. **Откат разговора согласован с результатом и оценкой.** Неизменившийся результат
   сохраняет оценку; смена предъявленного Message инвалидирует её.
8. **`User.stop()` закрывает допуск новых действий.** Уже допущенные модельный вызов
   и оценивание заканчиваются целиком; их нормальные возвраты сохраняются.
   Это не `LLMChat.cancel()`. Настоящая ошибка имеет приоритет над остановкой.
9. **Повторные запуски независимы.** Освобождение участников и завершение журнала
   принадлежат рабочему выполнению и не зависят от вызова наблюдателем `wait()`.
   Итоговые артефакты сохраняются снаружи.
10. **Сохраняется смысл бюджета:** `max_calls_per_conv` — библиотечные раунды Target,
    а не сумма обращений Target/Attacker/оценщика.

Перечисленные ограничения garak — причины, по которым наивная замена интеграции
нарушит контракты. Это не утверждение, что все такие runtime-нарушения уже
воспроизведены в текущем рабочем дереве.

Отдельное обязательство: README и ADR 0003 требуют настоящий FITD. Самостоятельно
переписанный похожий алгоритм нельзя молча представить как прежнюю библиотечную
реализацию. В закреплённом алгоритме есть особенности порядка проверок, индексации
лестницы и realignment; их «попутное исправление» изменит поведение.

исправление FITD и итоговая проверка остаются незавершёнными. При возобновлении

Публичные `redactor` и `diagnostic_settings` затем добавлены. Это не доказывает,
что все runtime-регрессии устранены. Продолжать учитывать запрет полного pytest.

## 6. Обсуждённые альтернативы и открытый вопрос

### 6.1. Последовательность уточнений пользователя

1. Исходная цель: исправить FITD для линтера, соблюдая уже зафиксированное требование
   абстрагироваться от garak, а не наследоваться от него.
2. Пользователь попросил объяснить изменения и возразил против потери переиспользования
   готовых функций при переходе на более низкий уровень. Агент признал, что собственный
   цикл tai перестанет использовать `IterativeProbe.probe()`, а необходимость именно
   выделения нового engine не доказана.
3. Пользователь: «Мы не будем менять garak. Если у нас нет возможности прокинуть свои
   колбеки в garak, значит будем работать с ним как с черным ящиком».
4. Затем пользователь изменил направление: «Мы по прежнему не будем редактировать
   garak, но мы спустимся на более низкий уровень чтобы иметь больше контроля за ходом
   атаки. Можем использовать инструменты garak, но эти инструменты тоже должны быть
   обернуты в наш интерфейс».
5. Агент пояснил, что самостоятельного FITD-engine с нужным API в исследованной ревизии
   нет, предложил собственную стратегию tai с обёрнутыми инструментами и спросил о
   допустимости переноса подготовки и переходов. **Ответ: пользователь пока не
   определился; поручил записать альтернативы и вопрос в handoff.**

### 6.2. Сводка вариантов

| Вариант | Что переиспользуется / цена | Статус |
| --- | --- | --- |
| A. Фасад над нашим подклассом `FITD` | Библиотечный алгоритм и цикл; остаются наследование и private hooks. | Текущий код. Не соответствует требованию пользователя. |
| B. Общий компонент алгоритма в изменённом garak | Штатный garak и tai используют одну реализацию подготовки/адаптации; цикл tai даёт контроль. Нужен патч зависимости, теряется вызов библиотечного `probe()`. | Предлагался, не согласован; исключён текущим запретом редактировать garak. |
| C. Расширение API самого `FITD` | Сохраняются готовые функции и `probe()`, добавляются явные зависимости, наблюдение и политика продолжения. | Предлагался после возражения о переиспользовании; также требует запрещённого сейчас изменения garak. |
| D. Неизменный `FITD` как чёрный ящик | Переиспользуются алгоритм и цикл целиком; контроль ограничен реальными входами/выходами, часть наших контрактов пересматривается. | Был выбран промежуточно; затем пользователь изменил направление. Не считать итоговым решением. |
| E. Низкоуровневые инструменты garak за нашими интерфейсами | Tai управляет подготовкой, переходами и циклом; garak предоставляет детектор и ресурсы. Это собственная реализация FITD. | Последнее обсуждавшееся направление. Перенос алгоритма пока не разрешён: пользователь не определился. |

Предложение добавить garak в `ignored-parents` снято. `MethodType`, подмена приватных
методов/глобальных служб и внедрение методов через config не являются согласованными
альтернативами композиции. Расширять Domain библиотечными методами ради `W9201` тоже
не предлагать как исправление архитектуры.

### 6.3. Вариант B: общий компонент в зависимости

Предлагалось выделить подготовку и адаптацию в самостоятельный компонент garak,
который вызывают **и штатный `garak.FITD`, и адаптер tai**. Компонент получает явную
задачу, зависимости и локальное состояние; предоставляет реальные проверки и выбор
продолжения. Tai владеет разговорами, принятием результата, оценкой, остановкой и журналом.

Обсуждались новая закреплённая upstream-ревизия с подходящим API, поддерживаемый
патч/fork либо ожидание upstream-изменений. Ни один путь поставки не согласован.
Для сохранения проверок при последующей ошибке компоненту нужны отдельные наблюдаемые
операции или пошаговый API; окончательной формы API не выбирали.

Цена варианта с циклом tai — отказ от переиспользования `IterativeProbe.probe()`.
Агент сначала назвал этот путь предпочтительным, затем признал, что это лишь один
вариант, а не доказанная необходимость. **К нему не возвращаться как к уже принятому
решению; он требует изменения ограничения пользователя.**

### 6.4. Вариант C: композиционный API на существующем `FITD`

Предлагалось оставить обычный объект `FITD` внутри `GarakRuntime` и сохранить
библиотечные функции и цикл. В самой библиотеке понадобились бы:

- явные исходные задачи, с HarmBench только как fallback;
- передаваемые участники и локальные службы вместо обязательной глобальной настройки;
- результаты refusal/alignment и фактического выбора продолжения;
- политика после выбора, позволяющая принять результат, оценить его и завершить запуск;
- контекст подготовленной попытки до отправки, включая неотправленное продолжение;
- управляемые границы остановки и распространение ошибок вместо их поглощения.

Точки изменений — `garak/probes/fitd.py` и часть `garak/probes/base.py`.
Это проектируемое расширение, **не существующий API**. Объём патча не оценён и
не проверен. Наследование внутри самой библиотеки не нарушало бы требования к tai,
но редактировать библиотеку пользователь запретил.

### 6.5. Вариант D: неизменный `FITD` как чёрный ящик

Обычная обёртка `StrategyRuntime -> GarakRuntime -> FITD.probe()` действительно
устраняет наследование tai и скрывает типы библиотеки. Она не может заставить
библиотеку вызывать отсутствующие в API callbacks: внутренний `self` остаётся `FITD`.

Предлагавшиеся изменения семантики:

- журнал наблюдает модельные обмены, их ошибки, внешний вызов и возвращённые данные;
  внутренние boolean-проверки и ветки не реконструируются по промптам/логам;
- разговор согласуется, когда Target получает очередной `Conversation`; обещание
  применить неотправленное продолжение последнего раунда снимается;
- внутреннее завершение определяет garak; оценщик tai оценивает предъявленный итог
  снаружи, а не управляет библиотечным циклом после принятия ветки;
- stop и исходная ошибка контролируются на доступных границах модельных мостов;
- предлагалось предъявлять последний завершённый ответ из возвращённых попыток и
  оценивать его один раз после штатного завершения. **Это правило не согласовано.**

**Уточнение к прежнему выводу о невозможности передать base.** Присваивание
`target_prompts` действительно перезаписывается, но найден кандидат на штатный
файловый вход: `garak/data/__init__.py` ищет ресурс сначала в пользовательском каталоге
`_config.transient.data_dir / "data"`, затем в поставке. Каталог определяется через
XDG. Предлагалось подготовить пользовательский `harmbench/harmbench_prompts.txt`
с единственной задачей и задать `initial_prompt_count=1`.

Это результат чтения исходников, **не проверенная работающая интеграция**.
FITD читает задачи через `splitlines()`, поэтому многострочный Message нельзя просто
записать туда как одну задачу. Ограничить адаптер однострочным вводом предлагалось,
но разрешение не получено; незаметно изменять текст нельзя.

Для изоляции XDG-ресурсов и глобальных служб предлагался отдельный процесс на запуск,
с мостами к LLMChat основного процесса, где могут оставаться веса Qwen. Такой worker,
IPC и smoke не реализованы. Это предложение относится к чёрному ящику, а не является
обязательной частью варианта E.

### 6.6. Вариант E: управляемая стратегия tai и обёрнутые инструменты

```text
Execution -> StrategyRuntime -> реализация FITD в tai
    -> наши интерфейсы инструментов
        -> адаптер garak.detectors.mitigation.Prefixes
        -> адаптер штатных FITD-ресурсов установленного garak
```

Самостоятельных builder/selector-функций FITD вне класса `FITD` в исследованной
поверхности не найдено. Прямой вызов `generate_next_turn_attempt()` всё ещё скрывает
внутренние проверки и требует лестницы, native notes и служб. Вызовы приватных
`FITD._…`, unbound-методов на собственном объекте или создание объекта в обход
конструктора не являются готовой независимой инструментальной границей.

**Реально найденные инструменты** (чтение установленного кода, без запуска):

- `garak/detectors/mitigation.py:199–240`: `Prefixes` можно создать напрямую и
  содержать внутри нашего адаптера, без plugin loader и наследования. Вход
  `detect()` — native `Attempt`, выход — список `float | None`; они остаются внутри
  адаптера. Наш контракт может быть `RefusalCheck(Message) -> bool`.
- Для каждой проверки нужен новый временный `Attempt` с prompt и output,
  явно помеченными `lang="en"`. Setter `outputs` добавляет реплики, поэтому
  переиспользование одного Attempt требует осторожности. Один вызов инструмента
  даёт один проверенный score; `None`, неверная форма и исключение не становятся `False`.
- Полярность `Prefixes`: найденный отказ даёт `0.0`, отсутствие — `1.0`;
  сохраняемый порог FITD — `< 0.5`. Default `matchtype="str"` ищет подстроку в любом
  месте без учёта регистра, несмотря на название детектора. Замена на `startswith`
  изменила бы поведение.
- `garak/data/fitd`: шесть шаблонов (initial safety, ladder, paraphrase, realignment,
  alignment, native evaluation) и `sensitive_words.csv`. Их можно читать через
  наш источник ресурсов/построитель промптов. Наличие native evaluation-шаблона
  не требует использовать его вместо оценщика tai.
- Предлагалась загрузка именно bundled-файлов через
  `importlib.metadata.distribution("garak").locate_file(...)`, чтобы не выбирать
  XDG overrides и не импортировать garak ради чтения данных. Это ещё не проверено
  smoke-тестом. `importlib.resources.files("garak")` по имени импортирует пакет.
- CSV нужно разбирать штатным `csv.reader`, сохраняя значения и порядок замен:
  в исходных данных есть необычное значение `killed"`; не исправлять его попутно.

Прямой детектор не использует language service, buffs, reportfile или модели при
`detect()`, но `{}` в `config_root` не устраняет все глобальные обращения конструктора.
Есть чтение `seed` и `system.verbose`; первый импорт garak инициализирует XDG-каталоги
и logging. Явные настройки детектора фиксируют поиск; не обещать полностью
безэффектный импорт. Эти особенности не требуют автоматически отдельного процесса.

**Что пришлось бы реализовать в tai:** подготовку initial turn и лестницы, retries,
замены слов, заполнение уровней, модельную alignment-проверку и разбор ответа,
выбор перехода, состояние прогресса и цикл раундов. Attacker/Target используются
через существующий `StrategyPorts.send`, история остаётся в LLMChat. Наблюдение
получает реальные `LocalDecision`, `BranchDecision`, `TargetExchange`,
`Synchronization`, `ResultChange`; составным операциям внедряются уже обёрнутые
зависимости вместо динамических подклассов.

Намеченная, **не реализованная** раскладка:

- сохранить `StrategyRuntime`, `StrategyPorts`, `ConversationPorts`;
- добавить собственные состояние, подготовленную попытку и runtime; заменить
  библиотечные generics в `contracts.py` независимыми контрактами;
- заменить `probe.py` и native-анализ в `continuation.py` операциями подготовки/выбора;
- переделать `target.py` на явные действия с checkpoint вместо native Conversation;
- подключить инструменты и обёртки в `bootstrap.py` / `experiment.py`;
- после переноса удалить ненужный native-мост/configuration, сократить stubs,
  обновить `observation.py` и карту Tach.

Предложено сохранять текущую семантику в первом переносе: порядок
refusal -> alignment -> realignment/продвижение, retries, заполнение уровней,
индексацию лестницы и бюджет Target. В частности, native код использует
`ladder[new_levels_completed + 1]`; обычный путь при трёх уровнях может быть
`initial -> q2 -> q3 -> goal -> goal`. Отрицательный alignment на realignment-запросе
может сопровождать `continue`. Это не разрешение попутно исправлять алгоритм.

Сохранение семантики нужно доказать сценариями, а не считать следствием переноса.
Опоры: `test_fitd_adaptation.py`, `test_fitd_operations.py`, `test_fitd_control.py`,
`test_fitd_stop_boundaries.py`, `test_fitd_worker.py`, `test_fitd_restart.py`,
`test_journal.py`, `test_evaluator_contract.py`, `test_model_evaluator_lifecycle.py`.
В `tests/fitd_observation.py` и `tests/journal_scenarios.py` перехват private hooks
потребуется заменить наблюдением реальных инструментов. Сравнение обёрнутого и
необёрнутого режимов дополнить ожидаемыми трассами, иначе оба могут одинаково
изменить поведение. Полный pytest по-прежнему не разрешён.

### 6.7. Главный открытый вопрос и последствия выбора

Последний вопрос агент сформулировал так:

> Правильно понимаю, что теперь допустим перенос подготовки лестницы и адаптивных
> переходов FITD в tai с использованием инструментов garak за нашими интерфейсами?

**Пользователь ещё не ответил утвердительно.** Его последний ответ — «Я пока не
определился» и поручение обновить handoff. Не начинать вариант E по умолчанию и
не считать промежуточное решение о чёрном ящике действующим разрешением на вариант D.

При выборе E нужно честно зафиксировать собственную реализацию FITD, а не продолжать
называть её исполнением библиотечного алгоритма. README прямо обещает библиотечные
подготовку и переходы; ADR 0003 требует настоящего многоходового FITD. Потребуются
актуальные формулировки и ADR о смене реализации. Исторические отчёты приёмки не
подтверждают новую реализацию. В метаданных следует различать версию стратегии tai
и ревизию используемых garak-инструментов.

При выборе D нужно явно согласовать изменения контрактов из 6.5, в частности
предъявленный результат, точки оценки, доступность внутренних событий и способ
передачи base. Ни правило «последний ответ», ни однострочный ввод пока не приняты.

Дополнительная семантическая деталь для любого переноса: нынешний `probe.py:197–206`
при успехе оценщика возвращает до `synchronize()`. Предлагалось сохранить это
поведение, сохраняя обязательное согласование при лимите раундов. Не распространять
гарантию final-round sync на завершение по успеху без отдельного рассмотрения.

Сверены задачи [#1](https://github.com/ArtFilippov/tai/issues/1),
[#18](https://github.com/ArtFilippov/tai/issues/18),
[#20](https://github.com/ArtFilippov/tai/issues/20). Старая #1 разрешала узкий подкласс;
позднее требование пользователя об устранении наследования имеет приоритет.
#18/#20 фиксируют реальные наблюдаемые операции, однократность решений и отсутствие
реконструкции журнала из private state. GitHub Issues в этой сессии не изменялись.

## 7. Порядок продолжения

1. Снять актуальные `git status` и diff; прочитать перечисленные контракты и
   отличить принятые требования от незавершённых решений агентов.
2. Вернуться к открытому вопросу 6.7 и получить выбор пользователя. Garak не менять;
   не считать вариант E или промежуточный D согласованным. После выбора оформить
   решение в domain/ADR-документации и явно перечислить пересматриваемые обязательства.
3. Разделить согласованную работу: стратегия/интеграция; независимые контракты/наблюдение;
   типизация и сохранение сценариев тестов; финальная карта зависимостей и качество.
   Назначить непересекающиеся файлы, изменения общих конфигураций сводить отдельно.
4. Устранить наследование и библиотечный API за пределами адаптера, соблюдая
   согласованные после выбора контракты. После этого пересмотреть необходимость
   фасада и stubs; проверить целевые сценарии без полного runtime-прогона.
5. Проверить и принять обновлённую карту слоёв; выполнить полный статический check.
   После правок `quality/` выполнить его регрессионные unittest. Полный runtime-набор
   запускать только после изменения пользовательского ограничения.
6. Сообщить фактический exit code и оставшиеся диагностики. Коммит — по отдельному
   поручению; новые изменения и этот handoff автоматически не коммитить.

Команды для согласованного продолжения, а не свидетельство их выполнения сейчас:

```bash
uv run --locked --group dev python quality/init_architecture.py --accept --json
uv run --locked --group dev python quality/check.py
uv run --locked --group dev python -m unittest discover -s quality/tests
```

В окружении, подготовленном для Qwen, сохранять `--extra qwen` в командах uv.
При необходимости изменения лимитов пользоваться `quality/readability.toml` и
`quality/apply.py --json`; разрешение на дальнейшее ослабление правил не дано.
